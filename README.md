# Tank Battle Online

Браузерная дуэль двух танков в духе Worms: атакующий наводит прицел, защитник
одновременно и вслепую решает, куда откатиться. Оба решения раскрываются
одновременно — снаряд летит туда, куда целились, а танк едет туда, куда решили.

## Стек

- Rails 7.1, Ruby 3.2.2 (rbenv), SQLite
- Devise — аутентификация
- Action Cable (`BattleChannel`) — состояние боя приходит обоим игрокам как JSON
- Stimulus + инлайновый SVG — прицеливание и анимация боя, без сторонних библиотек

## Запуск

```bash
export PATH="$HOME/.rbenv/shims:$PATH"   # если ruby 3.2.2 не в PATH по умолчанию
bundle install
bin/rails db:create db:migrate db:seed
bin/rails server
```

Открыть `http://localhost:3000` в двух разных браузерах (или обычное окно +
инкогнито — нужны две независимые сессии):

| Email | Пароль | Танк |
|---|---|---|
| player1@example.com | password123 | Al Capone (синий, слева) |
| player2@example.com | password123 | Lucky Luciano (красный, справа) |

Оба жмут «JOIN THE QUEUE» на странице персонажа (она же корень сайта) — как
только в очереди оказывается двое, бой начинается сам и обоих перебрасывает в
него без перезагрузки. Соперник всегда подбирается случайно; выбрать
конкретного противника нельзя — страница «Battles» показывает только историю
уже сыгранных и текущих боёв.

## Подбор соперника

Отдельной страницы лобби нет — сама очередь живёт на странице персонажа:
кнопка «JOIN THE QUEUE» ставит в неё через `POST /lobby/join`, тот же виджет
снимает через `POST /lobby/leave`. Встал в очередь и ждёшь; как только ждущих
становится двое, `Matchmaker` берёт тех, кто ждёт дольше всех, и сразу
открывает бой — подтверждать вызов не нужно, согласие уже дано самим фактом
записи. Пул на четверых превращается в два отдельных боя, пятый ждёт
следующего.

Захват пары сделан без блокировок БД: записи забираются по одной, и `delete_all`
сообщает, сколько строк реально удалил. Если партнёра успел забрать параллельный
запрос, своя заявка возвращается на место с прежним `created_at` — игрок не
теряет очередь и не выпадает из неё.

`LobbyChannel` (имя осталось от прежней страницы лобби, суть та же) держит две
подписки: личную (в неё приходит найденный бой, адресованный ровно одному
игроку) и общую (в ней только число ждущих — оно ничьё, поэтому его можно
вещать всем). Ответ на `POST /lobby/join` тоже несёт id боя: если сокет лежит,
игрок всё равно попадёт в бой.

Страница «Battles» — только список прошлых и текущих боёв игрока, без
возможности вызвать кого-то конкретного: единственный путь в новый бой —
очередь на странице персонажа.

Пока бой идёт, игрок из него не выходит: любая страница уводит обратно на бой,
записаться в очередь на второй бой нельзя. Отвечает за это
`ApplicationController#hold_player_in_battle` — он включён для всех контроллеров
сразу, поэтому новые страницы попадают под правило автоматически. Исключения
заданы путём: всё, что под `/battles/:id`, работает, Devise исключён (иначе не
выйти из аккаунта), а JSON-запросы получают `409` с `battleId` вместо редиректа.

## Правила

Поле — 100 единиц, ровная земля. Танки стартуют на отметках **20** и **80**,
длина танка — **5** единиц.

Каждый ход у игроков разные роли, и они меняются местами после каждого раунда:

- **Атакующий** не двигается. Ведёт мышью по полю — рисуется дуга траектории,
  крестик показывает точку падения. Стреляет кликом по полю или кнопкой FIRE.
  Подсвеченная полоса показывает, куда соперник успеет уехать.
- **Защитник** не стреляет. Встаёт в **любую точку в пределах ±9** от текущей
  позиции: клик по полосе сразу фиксирует ход, кнопки-пресеты делают то же
  самое. Наведение мышью только показывает вариант.

На ход даётся **30 секунд**, счётчик висит в шапке и краснеет на последних
десяти. Не успел — атакующий не стреляет, защитник остаётся на месте; раунд всё
равно разрешается. Поэтому бой нельзя заморозить, уйдя из него: пока ты
пропускаешь ходы, соперник продолжает по тебе бить. Вернуться можно в любой
момент — состояние подтянется само.

Обе стороны ходят одним движением — навёлся и кликнул, подтверждать нечего.
После хода игрок видит **свой** выбор золотым: атакующий — дугу в точку падения,
защитник — призрак танка на новом месте. Соперник этого не видит.

Пока оба не приняли решение, сервер **не показывает выбор соперника** — видно
только «противник уже решил». Когда пришли оба, раунд разрешается и у обоих
проигрывается анимация: снаряд летит по дуге, танк одновременно едет.

### Урон

Танк длиной 5 разбит на пять односегментных полос, плюс две полосы осколков
снаружи. Точное значение внутри полосы бросается случайно:

| Расстояние от центра | Куда попал | Урон |
|---|---|---|
| ≤ 0.5 | точно в центр | 25–30 |
| 0.5 – 1.5 | середина корпуса | 15–20 |
| 1.5 – 2.5 | край гусеницы | 5–10 |
| 2.5 – 3.5 | осколки рядом | 2–4 |
| 3.5 – 4.5 | осколки поодаль | 1–2 |
| > 4.5 | мимо | 0 |

При попадании над танком на 3 секунды всплывает нанесённый урон.

У защитника 19 возможных позиций (±9 от текущей). Полный урон снимает только
попадание почти в центр, а осколки хоть и достают мимо корпуса, но дают
единицы — уклонение по-прежнему окупается. Основная ставка та же: целясь ровно
в предполагаемую точку, получаешь 25–30 при угадывании и ноль при промахе;
целясь между вероятными позициями, накрываешь больше вариантов, но каждый — по
краю корпуса, за 5–10.

## Устройство

- `Battle` — всё состояние боя: HP, позиции, чей ход, номер раунда. Персонаж
  носит только шаблон характеристик, так что урон не утекает между боями.
- `BattleTurn` — один раунд: копит `aim_x` и `move_delta`, пока не заполнятся
  оба, затем `Battle#resolve_turn!` считает результат под `with_lock` (защита от
  гонки, если оба нажали одновременно).
- `battle_controller.js` — весь интерфейс боя: расстановка танков, дуга прицела,
  полёт снаряда, взрыв, стекание HP, переключение панелей.

### Как ходит состояние

Страница боя запрашивается у сервера **ровно один раз**. Дальше:

1. Игрок кликает по полю (или жмёт FIRE / пресет) → `fetch` POST'ом, ответ
   `204 No Content`.
2. `Battle#broadcast_state!` шлёт в `BattleChannel` полный JSON состояния.
3. Оба браузера применяют его одним и тем же кодом, что и начальное состояние.

Поэтому все панели (прицел, смещение, ожидание, результат) отрендерены в HTML
сразу и просто переключаются на клиенте — их разметка не зависит от того, чей
сейчас ход, так что дублировать её в JS не пришлось.

`state_payload` **без аргумента одинаков для обоих игроков**: незавершённое
решение попадает туда только как `committed: true`, никогда как значение.
Именно эта версия уходит в бродкаст, поэтому общий стрим безопасен, а
`BattleChannel` вдобавок отклоняет подписку не-участника.

Своё собственное решение игрок видеть должен — иначе после перезагрузки не
понять, куда стреляешь. Поэтому `state_payload(viewer)` добавляет секцию `you`
с решением **только этого** игрока, и вызывается она из двух мест: рендер
страницы и `GET /battles/:id/state`. Оба адресованы одному человеку. Бродкаст
`you` не несёт никогда.

### Таймер хода

Дедлайн лежит в `battle_turns.deadline_at` и проверяется **только сервером**
(`Battle#resolve_if_expired!`). Браузер показывает секунды и, дойдя до нуля,
шлёт `POST /battles/:id/expire` — но это лишь просьба: соврать о времени клиент
не может, а два пинка подряд разрешают ход один раз, потому что второй застаёт
уже новый дедлайн в будущем.

Фонового воркера нет намеренно. Если оба игрока ушли, ход просто ждёт, и
просроченный раунд разрешает первый вернувшийся (`battles#show` и
`battles#state` вызывают `resolve_if_expired!` на входе). Следующий ход при этом
стартует с полными 30 секундами: терять раунды, когда рядом не было соперника,
незачем.

Пока сокет лежит, бродкасты просто теряются, поэтому Action Cable сообщает
`connected: { reconnected: true }`, и клиент дозапрашивает состояние у
`/battles/:id/state`. Раунд, разрешившийся без нас, отыграется анимацией —
`seenReplayId` не даст проиграть уже виденный. На телефоне это основной сценарий:
блокировка экрана рвёт соединение каждый раз.

Ещё деталь: **в SVG нет ни одного серверного динамического значения** — всё
ставит JS. Сцена не переживала бы перерисовку посреди анимации.

## Тесты

RSpec + FactoryBot: модели (`spec/models`), Action Cable-каналы
(`spec/channels`, `type: :channel`) и контроллеры через request-специфики
(`spec/requests`) — не `type: :controller`, эта разновидность в текущем
rspec-rails устарела в пользу реальных HTTP-запросов через роуты. JS-контроллеры
(`app/javascript/controllers`) не покрыты сознательно: в проекте нет ни
package.json, ни JS-раннера — importmap-rails выбран именно чтобы не тащить
Node/сборку, заводить их ради трёх Stimulus-контроллеров не стали.

```bash
export PATH="$HOME/.rbenv/shims:$PATH"
bin/rails db:test:prepare   # подтягивает схему в storage/test.sqlite3
bundle exec rspec
```

`spec/models/battle_spec.rb` — самое важное место: там же лежит тест на
главный инвариант из этого файла («соперник не должен иметь возможности
читить») — он стабит `BattleChannel.broadcast_to` и проверяет, что пейлоад
никогда не несёт секцию `you` и решение приходит только как `committed: true`.
Если этот тест когда-нибудь покраснеет — значит инвариант сломан по-настоящему,
а не только в разметке. `spec/channels/battle_channel_spec.rb` проверяет тот же
периметр с другой стороны: что подписаться на чужой бой вообще нельзя.

`spec/requests/application_controller_spec.rb` фиксирует, что
`hold_player_in_battle` держит **любую** страницу без явного подключения —
включая корень (страницу персонажа), а не только `battles`/`lobby` — и что
Devise из-под стража исключён по имени, а не по пути: разлогиниться посреди
боя всё ещё можно.

`spec/models/matchmaker_spec.rb` включает один тест, который скорее
документирует риск, чем поведение: если в очередь каким-то образом попадёт не
готовый к бою персонаж (не через `LobbyController#join`, а мимо него), `accept!`
бросит исключение и `Matchmaker.run!` уронится на этой паре, не подобрав
никого дальше. В обычной игре так не бывает — `join` не пускает в очередь
не восстановившегося, а жизни сами не уменьшаются вне боя — но тест держит это
явным допущением, а не тихим фактом.

Случайный урон (`damage_for`) стабится через `allow(battle).to receive(:rand)`
там, где сценарию нужен предсказуемый исход боя — `rand` в `Battle` не
переопределён, поэтому стаб ложится прямо на `Kernel#rand`.

## Заметка про окружение (macOS, rbenv)

Ruby 3.2.2 из rbenv здесь собран под x86_64 и работает через Rosetta, а
системный компилятор таргетит нативный arm64. Это ломает нативные гемы
несовпадением архитектур при `dlopen`. Что сделано:

- `bootsnap` убран из Gemfile (не обязателен, только ускоряет boot).
- `bcrypt` собран вручную с явными флагами под x86_64 и лежит в gem-окружении
  rbenv 3.2.2 — обычный `bundle install` подхватывает готовую сборку.
- `concurrent-ruby` запинен на `1.3.5` из-за конфликта с `concurrent-ruby-ext`.

Если вылезет `LoadError: ... incompatible architecture`, чинить так же:
`gem uninstall <gem> -x`, затем
`gem install <gem> -- --with-cflags="-arch x86_64" --with-ldflags="-arch x86_64"`.
